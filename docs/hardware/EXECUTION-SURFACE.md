## Updater verification and installation boundaries

This section describes **only the extracted older updater**. `U@offset` means a
file offset in `bin/upgrade`, SHA-256
`d17809f33003856d66f5406e080081ca8f0e3954a8d5536bb8f541010b8cce1a`;
its corresponding text VA is `0x10000000 + offset`. `C@offset` means the file
offset/link-time VA in `lib/libsonoscrypto.so.1`, SHA-256
`03653fc9205ff23ad583506684f93387c444ac2b726a01bfa1ff18b6d7594c6c`.
ELF mappings and byte-checked disassembly are preserved in [images.json](evidence/execution-20261028/images.json).
Nearest-symbol labels in stripped code are not recovered function names.

1. **Two distinct signature handlers.** The 16-byte handler table at
   `U@0x1a2c0–0x1a39f` maps record `0xffffffff` to VA `0x100074e4` and record
   `0x11` to VA `0x100075c8`. Dispatch calls the selected callback at
   `U@0x7b30–0x7b50`. See [table](evidence/execution-20261028/record-handlers.json)
   and [dispatch](evidence/execution-20261028/upgrade-record-dispatch.dis.txt).
2. **Legacy RSA/MD5.** [Legacy handler](evidence/execution-20261028/upgrade-legacy-signature.dis.txt)
   `U@0x7580–0x75ac` finalizes a digest, passes scheme 1, hash selector 2,
   length 16 and the signature to `ZZ0109`, and requires result 1. Selector 2
   maps to MD5 in [hash wrappers](evidence/execution-20261028/crypto-hash.dis.txt)
   `C@0x53a0–0x5408,0x558c–0x5594`. [RSA wrapper](evidence/execution-20261028/crypto-rsa.dis.txt)
   `C@0x6a80–0x6b28` checks scheme/modulus/signature length and calls
   `mbedtls_rsa_rsassa_pkcs1_v15_verify`. This is a legacy verification path,
   not evidence that all packages use MD5, or that signatures can be bypassed.
3. **Legacy public trust anchor.** Main calls `ZZ0096` at `U@0x4898`;
   [loader](evidence/execution-20261028/crypto-legacy-key.dis.txt)
   `C@0x6b60–0x6b88` resolves a 162-byte DER public key via GOT VA `0x1c0b0`.
   Its R_PPC_RELATIVE addend points to `C@0xb2c4`. Host DER parsing yields
   RSA **1024 bits**, exponent **65537**, DER SHA-256
   `50ff475d72eeadbaef22fe0b83eb7dd1c566cbeed22e648aa9c7c09577949e15`.
   [Anchor metadata](evidence/execution-20261028/legacy-public-anchor.json) and
   [main setup](evidence/execution-20261028/upgrade-key-setup.dis.txt) preserve
   the derivation. This identifies a legacy anchor, not the entire envelope
   trust chain, key rotation policy or installed-device key.
4. **Sonos envelope verification.** [Envelope handler](evidence/execution-20261028/upgrade-envelope-signature.dis.txt)
   `U@0x767c` parses through `ZZ0121`; `U@0x76dc–0x772c` finalizes a 32-byte
   digest and passes callbacks plus hash selector 1 to `ZZ0124`.
   [Envelope entry](evidence/execution-20261028/crypto-envelope-entry.dis.txt)
   `C@0x8b34` calls `ZZ0125`; [verifier](evidence/execution-20261028/crypto-envelope-verifier.dis.txt)
   `C@0x8970–0x898c,0x8a70–0x8a8c` invokes key-selection and verification
   callbacks. The supplied verifier is `ZZ0110`, forwarding to `ZZ0109` at
   `C@0x6b48`. Selector 1 is SHA-256 in the hash/RSA wrappers. The
   [key selector](evidence/execution-20261028/crypto-envelope-key-selector.dis.txt)
   `C@0x70e8–0x7270` requires identifier type 3/length 20, compares two entries
   and rejects a matching entry when its deny mask intersects context bits
   `context[0] & 7`. The relocated table is at VA `0x1c018`, file `0xc018`.
   Both entries are 294-byte RSA-2048 public DER keys, exponent 65537, at
   `C@0xb490` (deny mask 1) and `C@0xb368` (deny mask 0). The caller initializes
   context word 1 at `U@0x76f8–0x7724`, so the first entry fails that mask gate.
   [Envelope anchor metadata](evidence/execution-20261028/envelope-public-anchors.json)
   records identifiers, offsets and DER hashes. This is a bounded static
   selection trace, not proof of runtime trust state, all envelope callers or
   installed-build applicability. The legacy 1024-bit key is a separate anchor.
5. **Hash coverage and verified older-package range.** [Stream helper](evidence/execution-20261028/upgrade-hash-stream.dis.txt)
   `U@0x5614–0x5664` updates active digest contexts. The [reader](evidence/execution-20261028/upgrade-payload-reader.dis.txt)
   `U@0x607c,0x6110–0x6114` gates hashing on its argument. The legacy handler
   reads signature bytes with a zero hash argument. The
   [header reader](evidence/execution-20261028/upgrade-header-reader.dis.txt)
   `U@0x638c–0x63f4` excludes signature headers by flags/type, then hashes ordinary
   original headers. The [unknown-record handler](evidence/execution-20261028/upgrade-unknown-record.dis.txt)
   `U@0x6ad4–0x6af0` consumes ordinary unknown sections through the same reader.
   A host cryptographic check verifies the old package's 128-byte signature at
   `0x482190` over exactly **`[0,0x482180)`**, using the recovered legacy public
   key and RSASSA-PKCS1-v1_5/MD5. Prefix MD5 is
   `08b5d59c20f82c96bfaf264b7ce4ac63`; altering its first byte is rejected
   ([signature validation](evidence/execution-20261028/legacy-signature-validation.json)).
   This proves that signature/range relationship for the pinned package, not
   model compatibility, independent signer attribution or a full runtime audit.
   Optional-record handling, compatibility/downgrade gates and all callers have
   not been audited end-to-end. No verify-before-every-write claim is made.
6. **Validation before the inspected local install call.** [Local wrapper](evidence/execution-20261028/upgrade-validate-install.dis.txt)
   `U@0x7ca8–0x7ccc` calls the parser and branches on a nonzero result before
   calling the install routine. The
   [direct-call inventory](evidence/execution-20261028/direct-callers.json) finds
   parser calls at `U@0x3094,0x7ca8` and installer calls at
   `U@0x3134,0x7ccc`. The [network phase functions](evidence/execution-20261028/upgrade-network-phases.dis.txt)
   keep parsing and installation separate. The
   [phase-state gate](evidence/execution-20261028/upgrade-phase-state.dis.txt)
   `U@0x2f68–0x2f90` permits action 3 only with state 4 and result zero;
   [network gating](evidence/execution-20261028/upgrade-network-phase-gates.dis.txt)
   `U@0x4288–0x42b4` checks that result before action 3 dispatch. The
   [dispatcher](evidence/execution-20261028/upgrade-phase-dispatch.dis.txt)
   `U@0x3298–0x329c` then selects the install phase. Completion handling at
   `U@0x2ff0–0x3008` stores action-2 result and advances state 3 to state 4.
   This narrows the normal sequential protocol gate; asynchronous/private-key
   variants, virtual dispatch, cancellation and every state writer remain open. These are all matching direct BL
   encodings in executable sections, not an exhaustive indirect-call inventory
   or proof of every coordinator/network path and time-of-check behavior.
7. **Slot/generation and writes.** [Installer](evidence/execution-20261028/upgrade-install.dis.txt)
   `U@0x5888–0x5924` reads bootsection and bootgeneration using fopen/fscanf,
   then reports destination `1 - section` and `generation + 1`. The strings
   are at `U@0x19aac,0x19acc,0x19aec`. It invokes the inline flash routine at
   `U@0x59d0`; [destination builder](evidence/execution-20261028/upgrade-slot-destination.dis.txt)
   `U@0x99f8` computes `1 - section`. This older rootfs lacks the requested
   `lib/libflash.so.1` path (extraction.json); the later Fenway library's offsets
   cannot describe this inline implementation. The
   [inline NAND writer](evidence/execution-20261028/upgrade-nand-writer.dis.txt)
   `U@0x8f94–0x8fa4` opens its supplied device O_RDWR, queries geometry through
   ioctl, and `U@0x9218–0x9220` checks the write return count. Its full preserved
   function range `U@0x8f10–0x952f` has no direct `read`/`memcmp` call, so the
   later-family userspace readback guarantee cannot be transferred to it.
   OOB-reading ioctls and possible kernel verification are separate; this is
   not proof that no verification exists. Complete OOB commit ordering,
   physical layout and power-loss behavior remain open.

The [package installation script](evidence/execution-20261028/package-install-script.txt)
is data only and was never run. Original lines 6–37 can remount JFFS, restore
selected files, save logs, remove files and sync; line 37 creates a conditional
reboot loop. Lines 40–108 can stop services/unmount filesystems and set a volatile
upgrade flag. Its existence is not a RAM-only custom-image boot facility.

Moggie's own updater uses a separate RSA-2048/SHA-256 scheme
(`firmware/updater/manifest.c:360–401`, `rsa.c:131–183`) and a placeholder key
(`pubkey_dev.h:1–13`). Its chooser writes persistent boot metadata
(`firmware/bootchooser/init:192–223,298–339`). Moggie's `bootslot`, `running_slot`,
`boot_ok`, two-attempt rule and custom A/B dimensions are **not stock findings**.
No stock `boot_ok` producer/consumer or health rollback rule is established here.

## Later encrypted envelope: completed host-only framing experiment

The 57.23 type-3/6/4 payloads each have a **314-byte**, big-endian `886499ca`
header with version 1, zero attributes, one recipient, a 20-byte type-3
identifier, wrapping algorithm ID 1 and a 256-byte wrapped blob. Cipher ID is 1;
no cipher-name claim is made. Their data sizes are 175,696 / 708,640 /
4,571,168 bytes respectively. The rootfs data starts at package file offset
`0xfcbc1`; this is not a decoded filesystem offset. These fields are read with
explicit bounds, without decrypting anything
([encrypted-headers.json](evidence/execution-20261028/encrypted-headers.json)).

The older [payload loader](evidence/execution-20261028/upgrade-encrypted-payload.dis.txt)
`U@0x64d4–0x6504` handles outer flag 4, rejects the signature/encrypted combination,
and requires a nonzero supplied context; the absent-context branch at
`U@0x6764–0x6784` returns error 48. It parses the header through `ZZ0053` at
`U@0x6718`, then initializes decryption through `ZZ0052` at `U@0x67a4`.
The captured [header parser](evidence/execution-20261028/crypto-encrypted-parser.dis.txt)
`C@0xa828–0xa8c0` checks that same magic/version and bounds the rest of the
structure; matching these fields establishes a format lead, not cross-version
implementation equivalence.

[Decryption setup](evidence/execution-20261028/crypto-encrypted-setup.dis.txt)
`C@0xae28–0xae88` obtains its key through the supplied callback then calls
`ZZ0075`. The supplied `ZZ0070` at `C@0xaee0–0xaee8` returns its first argument
unchanged; it does not derive a key from public signature anchors.
The [RSA decrypt wrapper](evidence/execution-20261028/crypto-rsa-decrypt.dis.txt)
`C@0x5bac–0x5c10` uses RSA private operation mode 1, and for scheme 1 configures
OAEP with hash selector 4 before `mbedtls_rsa_pkcs1_decrypt`. This is evidence of
a required caller-supplied RSA private-operation capability in this older path;
its provisioning/source and 57.23 applicability remain unproved. No private
key or decrypted key/payload was read, recovered or generated.

**Result:** the queued host-only experiment now establishes bounded header
structure and a concrete captured decryption gate. It does not produce a decoded
later rootfs, prove device access is necessary, or establish impossibility of
other offline extraction. Further progress needs a non-secret provisioning
trace or already-decoded matching capture; a magic-search miss is insufficient.

## Ranked zero-write routes and safest next experiment

No route below has demonstrated owner-code execution without persistent writes.
Ranking is engineering judgment about useful follow-up evidence and intervention
risk, not measured success probabilities.

| Rank | Route | Evidence / present verdict | Next proof required |
|---|---|---|---|
| 1 | Existing runtime volatile hook/service | RAM-backed aliases exist in the old image; no reachable arbitrary-program loader established | Matching build, actual callable hook, privileges, volatile backing and all associated writes |
| 2 | NFS-root boot | Old kernel wrapper contains `root=/dev/nfs rw ip=on` at `0x5000` | Literal is only a lead; active cmdline use, compiled client support and an exposed selection mechanism remain unknown |
| 3 | Recovery/maintenance RAM image | Boot sections and updater interfaces exist; no RAM-only loader proved | Recovery entry, signature policy, watchdog and absence of repair/state writes |
| 4 | TFTP/network boot | Brief supplies only version/echo/test as exposed commands; no loader proved | Captured bootloader implementation and reachable command/automatic mode; no hidden-command or network probing authorized |
| Exclude as zero-write | `/jffs/Configure`, Configure.dev and official update/install | Persistent hooks, earlier writes and flash/update effects above | These may matter to eventual installation; they do not satisfy this task's zero-write condition |
| Exclude as stock proof | Moggie chooser/updater | Custom source with persistent metadata and image writes | Already requires replacement-firmware execution |

**Single safest next supervised experiment:** host-only completion of the
older updater's inline OOB/partition-table commit ordering and its kernel
ioctl consumers, using the preserved writer and original captured bytes.
Expected result: a source-bound sequence of validity/generation transitions,
or a precise missing-kernel-code boundary. The legacy prefix signature and
normal sequential phase gate are now evidenced; asynchronous paths remain open. The later-envelope framing experiment above is
complete within its stated bounds; decoding remains open. Do not execute any
package program, script or device operation to close a gap. No live experiment
is justified as zero-write by this report.

## CONFIDENCE

- **High, version-bounded:** old init instructions, persistent write sites,
  package boundaries, kernel identities, FDT properties, legacy public-key
  location/parameters, the older offline signature/range and preserved call sites. Evidence is static
  and bound to the exact hashes above; no runtime outcome is implied.
- **High, capture-bounded:** ZP5S banner and S0/S1/KP/G/handoff messages exist in
  the extended log. No firmware version, Linux health or rollback policy follows
  from those messages alone.
- **Incomplete:** envelope trust provenance, authenticated byte ranges across
  all callers, watchdog and flash commit ordering. No exhaustive verification
  inventory or current-device trust claim is made.
- **Provisional:** route priorities and expected information value.

## UNKNOWN-OFFLINE

1. Exact installed 57.10 `-1-16` rootfs/kernel and model/capture provenance;
   deciphering a different-version package would still not prove that build.
2. Actual mount table, physical partition map, NOR identity/residency, MTD
   aliases, on-flash metadata and VNB applicability to this device.
3. All updater entry paths, authenticated ranges, all-caller envelope anchors/rotation,
   pre/post-write checks, rollback/downgrade rules and power-loss ordering.
4. U-Boot verification primitive/key, generation ties/wrap/fallback semantics,

5. Complete watchdog/reset/supervision behavior and runtime code-loading hooks.
6. NFS/TFTP/recovery/debug support **and reachability**, and all incidental
   persistent writes. No hardware/network action is authorized to resolve these.
