The persistent boot hook is **not a zero-write bootstrap**: supplying it requires
persistent file access, and earlier init stages already attempt persistent
writes. Even without repartition/format branches, Srandom runs before that hook.

The rootfs image is SquashFS, but [fstab](evidence/execution-20261028/etc-fstab.txt)

root encryption, mount options, aliases into other media and `/dev/nandjffs`
physical backing remain unverified. It would be wrong to resolve that conflict
using the other family's compiled cmdline. The bounded supervision paths below
do not yet establish complete watchdog/feeder or reset ownership.

## Older application supervision and reset paths

`A@offset` is a file offset in the additionally recovered older `opt/bin/anacapad`,
SHA-256 `9db3247f232fa7e2dd1a42561782d38b95c6c4905029f16b22293471d6f23870`.
Its text VA is `0x10000000 + offset`; images.json records its ELF mapping.
No application or driver was executed.

The captured `modules/chk_driver.o` is a relocatable ELF, not a ready-linked
executable. Its [complete text](evidence/execution-20261028/driver-text.dis.txt)
and [relocation records](evidence/execution-20261028/driver-relocations.json)
show character-device registration (major 243), trivial open/release, and
ioctl low-byte 1/2 read/write of the four-byte common RAM symbol `sysword`.
The preserved module has no timer, hardware watchdog feed or reset operation.
Relocation annotations identify external calls; an unresolved `bl` to the same
section offset must not be mistaken for recursion or a final linked target.
The application's [startup check](evidence/execution-20261028/anacapa-chk-startup.dis.txt)
reads `/dev/chk` with ioctl `0x4004f301` and compares the result with `0x1996`
(`A@0x5c68–0x5cec`). That establishes a RAM-word consumer, not an owner-code hook
or a complete account of which process writes the word.

The application also contains a distinct
[supervision loop](evidence/execution-20261028/anacapa-watchdog-supervision.dis.txt).
It samples registered callbacks on an approximately ten-second cadence and
passes a failing callback's result to the action routine
(`A@0x2e4258–0x2e434c`). The
[action routine](evidence/execution-20261028/anacapa-watchdog-action.dis.txt)
formats `WATCHDOG: ... unresponsive!`, opens `%s/watchdog.log` and
`%s/watchdog.dmesg` for creation/truncation, copies diagnostic data, and calls
fsync (`A@0x2e3e18–0x2e3f20`). Its prefix is caller-supplied in the
[setup](evidence/execution-20261028/anacapa-watchdog-setup.dis.txt)
(`A@0x2e4858`); its backing media cannot be inferred from the format alone.
Action `-2` raises signal 9; action `-3` syncs and invokes `/sbin/reboot`
through system (`A@0x2e3f24–0x2e3fc0`).
The [saved literals](evidence/execution-20261028/supervision-literals.json)
and all excerpts are independently checked against the recovered source bytes.

Two other captured paths explicitly log RDM watchdog reset messages, then call
the same reset helper:
[handler](evidence/execution-20261028/anacapa-rdm-reset-handler.dis.txt)
`A@0xb07c–0xb09c` and
[deadline branch](evidence/execution-20261028/anacapa-rdm-watchdog.dis.txt)
`A@0x56c5c–0x56c9c`. The
[helper](evidence/execution-20261028/anacapa-reboot.dis.txt)
syncs, sleeps and calls reboot with `0x01234567` (`A@0x1c6524–0x1c6544`).
These are concrete application reset requests. Registered client coverage,
all triggers, any separate hardware watchdog and successful-boot/rollback
coupling remain unknown; a `watchdog` string alone cannot establish them.

## Updater verification and installation boundaries

This section describes **only the extracted older updater**. `U@offset` means a
file offset in `bin/upgrade`, SHA-256
`d17809f33003856d66f5406e080081ca8f0e3954a8d5536bb8f541010b8cce1a`;
its corresponding text VA is `0x10000000 + offset`. `C@offset` means the file
offset/link-time VA in `lib/libsonoscrypto.so.1`, SHA-256
`03653fc9205ff23ad583506684f93387c444ac2b726a01bfa1ff18b6d7594c6c`.
ELF mappings and byte-checked disassembly are preserved in [images.json](evidence/execution-20261028/images.json).
Nearest-symbol labels in stripped code are not recovered function names.

1. **Two distinct signature handlers.** The 16-byte handler table at
   `U@0x1a2c0–0x1a39f` maps record `0xffffffff` to VA `0x100074e4` and record
   `0x11` to VA `0x100075c8`. Dispatch calls the selected callback at
   `U@0x7b30–0x7b50`. See [table](evidence/execution-20261028/record-handlers.json)
   and [dispatch](evidence/execution-20261028/upgrade-record-dispatch.dis.txt).
2. **Legacy RSA/MD5.** [Legacy handler](evidence/execution-20261028/upgrade-legacy-signature.dis.txt)
   `U@0x7580–0x75ac` finalizes a digest, passes scheme 1, hash selector 2,
   length 16 and the signature to `ZZ0109`, and requires result 1. Selector 2
   maps to MD5 in [hash wrappers](evidence/execution-20261028/crypto-hash.dis.txt)
   `C@0x53a0–0x5408,0x558c–0x5594`. [RSA wrapper](evidence/execution-20261028/crypto-rsa.dis.txt)
   `C@0x6a80–0x6b28` checks scheme/modulus/signature length and calls
   `mbedtls_rsa_rsassa_pkcs1_v15_verify`. This is a legacy verification path,
   not evidence that all packages use MD5, or that signatures can be bypassed.
3. **Legacy public trust anchor.** Main calls `ZZ0096` at `U@0x4898`;
   [loader](evidence/execution-20261028/crypto-legacy-key.dis.txt)
   `C@0x6b60–0x6b88` resolves a 162-byte DER public key via GOT VA `0x1c0b0`.
   Its R_PPC_RELATIVE addend points to `C@0xb2c4`. Host DER parsing yields
   RSA **1024 bits**, exponent **65537**, DER SHA-256
   `50ff475d72eeadbaef22fe0b83eb7dd1c566cbeed22e648aa9c7c09577949e15`.
   [Anchor metadata](evidence/execution-20261028/legacy-public-anchor.json) and
   [main setup](evidence/execution-20261028/upgrade-key-setup.dis.txt) preserve
   the derivation. This identifies a legacy anchor, not the entire envelope
   trust chain, key rotation policy or installed-device key.
4. **Sonos envelope verification.** [Envelope handler](evidence/execution-20261028/upgrade-envelope-signature.dis.txt)
   `U@0x767c` parses through `ZZ0121`; `U@0x76dc–0x772c` finalizes a 32-byte
   digest and passes callbacks plus hash selector 1 to `ZZ0124`.
   [Envelope entry](evidence/execution-20261028/crypto-envelope-entry.dis.txt)
   `C@0x8b34` calls `ZZ0125`; [verifier](evidence/execution-20261028/crypto-envelope-verifier.dis.txt)
   `C@0x8970–0x898c,0x8a70–0x8a8c` invokes key-selection and verification
   callbacks. The supplied verifier is `ZZ0110`, forwarding to `ZZ0109` at
   `C@0x6b48`. Selector 1 is SHA-256 in the hash/RSA wrappers. The
   [key selector](evidence/execution-20261028/crypto-envelope-key-selector.dis.txt)
   `C@0x70e8–0x7270` requires identifier type 3/length 20, compares two entries
   and rejects a matching entry when its deny mask intersects context bits
   `context[0] & 7`. The relocated table is at VA `0x1c018`, file `0xc018`.
   Both entries are 294-byte RSA-2048 public DER keys, exponent 65537, at
   `C@0xb490` (deny mask 1) and `C@0xb368` (deny mask 0). The caller initializes
   context word 1 at `U@0x76f8–0x7724`, so the first entry fails that mask gate.
   [Envelope anchor metadata](evidence/execution-20261028/envelope-public-anchors.json)
   records identifiers, offsets and DER hashes. This is a bounded static
   selection trace, not proof of runtime trust state, all envelope callers or
   installed-build applicability. The legacy 1024-bit key is a separate anchor.
5. **Hash coverage and verified older-package range.** [Stream helper](evidence/execution-20261028/upgrade-hash-stream.dis.txt)
   `U@0x5614–0x5664` updates active digest contexts. The [reader](evidence/execution-20261028/upgrade-payload-reader.dis.txt)
   `U@0x607c,0x6110–0x6114` gates hashing on its argument. The legacy handler
   reads signature bytes with a zero hash argument. The
   [header reader](evidence/execution-20261028/upgrade-header-reader.dis.txt)
   `U@0x638c–0x63f4` excludes signature headers by flags/type, then hashes ordinary
   original headers. The [unknown-record handler](evidence/execution-20261028/upgrade-unknown-record.dis.txt)
   `U@0x6ad4–0x6af0` consumes ordinary unknown sections through the same reader.
   A host cryptographic check verifies the old package's 128-byte signature at
   `0x482190` over exactly **`[0,0x482180)`**, using the recovered legacy public
   key and RSASSA-PKCS1-v1_5/MD5. Prefix MD5 is
   `08b5d59c20f82c96bfaf264b7ce4ac63`; altering its first byte is rejected
   ([signature validation](evidence/execution-20261028/legacy-signature-validation.json)).
   This proves that signature/range relationship for the pinned package, not
   model compatibility, independent signer attribution or a full runtime audit.
   Optional-record handling, compatibility/downgrade gates and all callers have
   not been audited end-to-end. No verify-before-every-write claim is made.
6. **Validation before the inspected local install call.** [Local wrapper](evidence/execution-20261028/upgrade-validate-install.dis.txt)
   `U@0x7ca8–0x7ccc` calls the parser and branches on a nonzero result before
   calling the install routine. The
   [direct-call inventory](evidence/execution-20261028/direct-callers.json) finds
   parser calls at `U@0x3094,0x7ca8` and installer calls at
   `U@0x3134,0x7ccc`. The [network phase functions](evidence/execution-20261028/upgrade-network-phases.dis.txt)
   keep parsing and installation separate. The
   [phase-state gate](evidence/execution-20261028/upgrade-phase-state.dis.txt)
   `U@0x2f68–0x2f90` permits action 3 only with state 4 and result zero;
   [network gating](evidence/execution-20261028/upgrade-network-phase-gates.dis.txt)
   `U@0x4288–0x42b4` checks that result before action 3 dispatch. The
   [dispatcher](evidence/execution-20261028/upgrade-phase-dispatch.dis.txt)
   `U@0x3298–0x329c` then selects the install phase. Completion handling at
   `U@0x2ff0–0x3008` stores action-2 result and advances state 3 to state 4.
   This narrows the normal sequential protocol gate; asynchronous/private-key
   variants, virtual dispatch, cancellation and every state writer remain open. These are all matching direct BL
   encodings in executable sections, not an exhaustive indirect-call inventory
   or proof of every coordinator/network path and time-of-check behavior.
7. **Slot/generation and writes.** [Installer](evidence/execution-20261028/upgrade-install.dis.txt)
   `U@0x5888–0x5924` reads bootsection and bootgeneration using fopen/fscanf,
   then reports destination `1 - section` and `generation + 1`. The strings
   are at `U@0x19aac,0x19acc,0x19aec`. It invokes the inline flash routine at
   `U@0x59d0`; [destination builder](evidence/execution-20261028/upgrade-slot-destination.dis.txt)

   `lib/libflash.so.1` path (extraction.json); the later Fenway library's offsets
   cannot describe this inline implementation. The
   [alternate userspace writer](evidence/execution-20261028/upgrade-nand-writer.dis.txt)
   `U@0x8f94–0x8fa4` opens its supplied device O_RDWR, queries geometry through
   ioctl, and `U@0x9218–0x9220` checks the write return count. Its full preserved
   function range `U@0x8f10–0x952f` has no direct `read`/`memcmp` call, so the
   later-family userspace readback guarantee cannot be transferred to it.
   That function is called on a different installer branch (`U@0x5b0c,0x5b50`);
   it is not the complete partition-table installation path. The latter calls
   the separate `U@0x85c8` writer, traced next. This distinction narrows the
   earlier handoff's wording. Kernel verification, physical layout and
   power-loss behavior require their own evidence.

The [package installation script](evidence/execution-20261028/package-install-script.txt)
is data only and was never run. Original lines 6–37 can remount JFFS, restore
selected files, save logs, remove files and sync; line 37 creates a conditional
reboot loop. Lines 40–108 can stop services/unmount filesystems and set a volatile
upgrade flag. Its existence is not a RAM-only custom-image boot facility.

Moggie's own updater uses a separate RSA-2048/SHA-256 scheme
(`firmware/updater/manifest.c:360–401`, `rsa.c:131–183`) and a placeholder key
(`pubkey_dev.h:1–13`). Its chooser writes persistent boot metadata
(`firmware/bootchooser/init:192–223,298–339`). Moggie's `bootslot`, `running_slot`,
`boot_ok`, two-attempt rule and custom A/B dimensions are **not stock findings**.
No stock `boot_ok` producer/consumer or health rollback rule is established here.

## Older partition writer and matching kernel metadata consumer

`K@offset` is a file offset in the decompressed **older** kernel, SHA-256
`c0a562fa670d1f620c249c8e5857388a575d85fa4fe3f5ce587720719509bf51`.
The [raw-kernel map](evidence/execution-20261028/kernel-map.json) recovers the
consistent `0xc0000000` link-label base from six export function/name pairs,
including `default_mtd_readv` at pair file `0x15ca48`. This is not an ELF header
or observation of a live load address. Each saved raw disassembly row is
checked against file bytes, separately from the ELF mappings.

**The table-based installation path programs partitions through `U@0x85c8`.** The
[destination commit sequence](evidence/execution-20261028/upgrade-commit-sequence.dis.txt)
`U@0x9d20–0x9d34,0x9d78–0x9d8c` passes `generation + 1` to VA `0x100085c8`.
The [partition writer](evidence/execution-20261028/upgrade-slot-program.dis.txt)
opens `/dev/mtd/0` (`U@0x8654–0x8668`, literal `U@0x1a4dc`), checks bad-block
markers through OOB-read ioctl `0xc00c4d04`, and erases 16 KiB at block boundaries
(`U@0x88d4–0x89dc`). Existing partition-table fields determine the start/end;
these are not a measured physical map for the speaker.

For the ordinary branch with table flag bit 0 clear, the OOB bytes built at
`U@0x870c–0x8754` are:

| OOB byte(s) | Captured writer value | Matching captured kernel check |
|---|---|---|
| 8–9 | `19 74`, or `74 19` at the final allocated partition page (`U@0x8838–0x8844`) | `K@0xc0254–0xc027c` accepts those two byte sequences |
| 10–11 | Generation, **low byte first** (`U@0x8724–0x873c`) | `K@0xc0290–0xc02a0` reconstructs byte 10 OR byte 11 shifted left 8 and rejects zero |
| 12–14 | Payload/page count expression, least-significant byte first (`U@0x8728–0x874c`) | Full semantics not reconstructed here; do not substitute Fenway LBLOCK fields |
| 15 | Zero (`U@0x8748–0x8754`) | Not assigned a boot-policy meaning here |

This is concrete counter-evidence to carrying the Fenway OOB map into this older
family: its magic/generation positions and generation endianness differ. The
captured kernel's [partition checker](evidence/execution-20261028/kernel-rincon-partition.dis.txt)
rejects read failure, bad magic, zero generation, generation mismatch and an
unfinished partition; its diagnostic strings name `nand_rincon_check_partition`
(`K@0x13cdf0–0x13cee0`). It accepts a `74 19` marker after consistent generation
checks (`K@0xc02b0–0xc0314`). For a valid partition-table magic, the ordinary
`19 74` path also checks the end page (`K@0xc02f8–0xc0338`); a separate legacy
branch can accept earlier. This is a **kernel** routine, not a disassembly of
U-Boot or proof of its fallback rules.

The matching [MTD dispatcher](evidence/execution-20261028/kernel-ioctl-dispatch.dis.txt)
recognizes `0xc00c4d03/04` at `K@0xb7440–0xb7478` and dispatches OOB writes and
reads to [write](evidence/execution-20261028/kernel-oob-write.dis.txt) and
[read](evidence/execution-20261028/kernel-oob-read.dis.txt) handlers.
The write handler copies the 12-byte descriptor and data, then calls the
MTD callback at object offset `0x124` (`K@0xb7870–0xb7890`). The
[NAND setup](evidence/execution-20261028/kernel-nand-callbacks.dis.txt)
`K@0xbe4e0–0xbe4ec` installs VA `0xc00bb268` into that field in the generic NAND
scan path. Its [OOB primitive](evidence/execution-20261028/kernel-nand-oob-program.dis.txt)
issues command `0x80`, writes the bytes, issues `0x10`, waits/checks status, then
issues `0x50` and invokes the verification callback (`K@0xbb368–0xbb47c`).
The captured [board initialization](evidence/execution-20261028/kernel-board-nand-init.dis.txt)
stores its allocated MTD object at VA `0xc017259c`, installs chip command/ready
callbacks and calls exported `nand_scan` (`K@0x16c1fc–0x16c27c`). On success it
registers that object with `add_mtd_device`, runs partition discovery, then
calls `add_mtd_partitions` (`K@0x16c288–0x16c2ec`). The partition checker loads
the same global object. This binds the generic OOB setup to this captured board
path; it does not measure the speaker's current MTD aliases or close every
error/retry path.

**Commit-order limit:** the partition writer issues the OOB-write ioctl at
`U@0x8774` before the associated 512-byte payload write at `U@0x887c`.
The end marker is selected before that ioctl. This source order is insufficient
to claim an atomic payload-plus-marker commit or power-cut-safe installation.
Complete error/retry behavior and bootloader validation remain open. No flash
operation was executed.

**Partition-table replacement precedes partition programming in the changing-table
branch.** The expanded [commit sequence](evidence/execution-20261028/upgrade-commit-sequence.dis.txt)
compares old/new table fields at `U@0x9bf0–0x9c08` through the
[table comparison helper](evidence/execution-20261028/upgrade-partition-table-compare.dis.txt).
A difference reaches `U@0x9c64–0x9c9c`, which calls the
[table writer](evidence/execution-20261028/upgrade-partition-table-write.dis.txt).
That helper opens `/dev/mtd/0`, maps logical good block 1 through the
[block mapper](evidence/execution-20261028/upgrade-logical-block-map.dis.txt),
erases 16 KiB, seeks and writes 512 table bytes (`U@0x8acc–0x8b44`).
The immediate caller does not test the helper's return value before branching
on its earlier partition-presence conditions (`U@0x9c9c–0x9ca8`). This local
observation does not prove all downstream error handling.

It then applies vendor ioctl `0x80084d22` to destination partition descriptors
and calls the [range invalidator](evidence/execution-20261028/upgrade-range-invalidate.dis.txt)
at `U@0x9cf4`, before the component writer calls at
`U@0x9eec,0x9f90,0x9d34,0x9d8c`. For good blocks, that invalidator erases 16 KiB
and submits an OOB prefix `85 19 03 20 08 00 00 00` at bytes 8–15
(`U@0x8ce8–0x8d28,0x8e60–0x8eb4`); the earlier partition checker rejects its
magic. Existing bad blocks are skipped. The equal-table branch skips that
table-replacement/invalidation sequence. These ordered calls establish a
non-atomic source sequence, not a complete power-cut outcome model; exact
on-device tables and bootloader consumers remain unknown.

**The vendor ioctls above manipulate partition RAM state.** The
[partition callback setup](evidence/execution-20261028/kernel-partition-callbacks.dis.txt)
installs callbacks at offsets `0x158/0x15c/0x160`
(`K@0xb6898–0xb68b8`), reached by the saved
[ioctl dispatch](evidence/execution-20261028/kernel-vendor-ioctls.dis.txt):

| Ioctl | Captured callback effect |
|---|---|
| `0x20004d20` | [Allocate buffers and read the partition into RAM](evidence/execution-20261028/kernel-partition-snapshot.dis.txt), publishing the cache pointer only after successful complete reads (`K@0xb58d8–0xb5a08`) |
| `0x20004d21` | [Free cached blocks and clear the cache pointer](evidence/execution-20261028/kernel-partition-free-adjust.dis.txt) (`K@0xb5608–0xb5680`) |
| `0x80084d22` | Store the supplied size and offset in the partition object (`K@0xb5694–0xb56a4`); this callback contains no flash operation |

[Partition reads](evidence/execution-20261028/kernel-partition-read-cache.dis.txt)
copy from that RAM cache when present (`K@0xb573c–0xb5844`); otherwise they
forward to the parent MTD read callback. The updater's
[adjust helper](evidence/execution-20261028/upgrade-partition-adjust.dis.txt)
submits the offset/size ioctl at `U@0x97d8–0x97f0`, and its commit path requests
the root partition snapshot at `U@0x9f58–0x9f70` before writing it. These are
in-memory snapshot/remapping mechanisms, not an extra on-flash commit marker.

**Data verification occurs in the matching kernel.** The captured
[character-device write](evidence/execution-20261028/kernel-char-write.dis.txt)
calls MTD offset `0x114` (`K@0xb71c0–0xb71e4`). The NAND setup points that
field to the [write wrapper](evidence/execution-20261028/kernel-nand-write-wrapper.dis.txt),
which calls the [data writer](evidence/execution-20261028/kernel-nand-data-write.dis.txt).
That writer programs pages through the
[page primitive](evidence/execution-20261028/kernel-nand-page-program.dis.txt)
and invokes the [readback verifier](evidence/execution-20261028/kernel-nand-data-verify.dis.txt)
before reporting completion (`K@0xbcba4,0xbcc08–0xbcc10,0xbccdc–0xbcce4`).
The primitive issues program command `0x10` and checks status
(`K@0xbbaa0–0xbbaec`); the verifier issues read command 0 and compares expected
data through chip callback `0x20` (`K@0xbbb54–0xbbbac`).
[NAND defaults](evidence/execution-20261028/kernel-nand-defaults.dis.txt)
bind that callback to an 8-bit or 16-bit
[device-buffer comparison](evidence/execution-20261028/kernel-nand-verify-buffer.dis.txt)
(`K@0xbdd08–0xbdd2c,0xbaa18–0xbaa9c,0xbab14–0xbab60`).
This establishes a captured kernel readback path behind the userspace write.
It neither authenticates the payload nor makes separate OOB/table/data writes
atomic, and it does not prove current-device execution of this code.

## Older kernel boot-section choice

The matching [partition discovery](evidence/execution-20261028/kernel-partition-discovery.dis.txt)
reads a 512-byte table with magic `0x653503e4` from logical good block 1 and
uses table flags to choose direct or bad-block-adjusted ranges
(`K@0xc0564–0xc06b0`). With no valid table magic, its legacy branch checks
blocks 16 through 63 and publishes that generation (`K@0xc06b4–0xc06f4`).
These are code paths and default ranges, not the speaker's measured layout.

With a valid table, the [section-choice routine](evidence/execution-20261028/kernel-boot-section-choice.dis.txt)
groups entries at type `0x40` boundaries and checks component types `0x10–0x12`
through the partition checker. A failing component or inconsistent generation
invalidates that group (`K@0xc070c–0xc07dc`). At `K@0xc07f0–0xc0868`, it chooses
section 1 only if its generation is greater than section 0's; otherwise it
chooses section 0 if that generation is positive. Thus a valid tie selects
section 0 in this kernel path. If neither is good, it reaches the `No good boot
section` failure. There is no generation-wrap adjustment in this comparison.
The stores publish VA `0xc0172598` (section) and `0xc0172594` (generation),
matching the `bootsection`/`bootgeneration` sysctl table entries at
`K@0x14db70,0x14db9c`.

This is Linux-side selection of partitions after kernel entry. It does not
establish which kernel U-Boot loads, U-Boot tie/wrap/fallback rules, a successful
userspace-health acknowledgement, or an attempt-counter rollback policy.

## Later encrypted envelope: completed host-only framing experiment

The 57.23 type-3/6/4 payloads each have a **314-byte**, big-endian `886499ca`
header with version 1, zero attributes, one recipient, a 20-byte type-3
identifier, wrapping algorithm ID 1 and a 256-byte wrapped blob. Cipher ID is 1;
no cipher-name claim is made. Their data sizes are 175,696 / 708,640 /
4,571,168 bytes respectively. The rootfs data starts at package file offset
`0xfcbc1`; this is not a decoded filesystem offset. These fields are read with
explicit bounds, without decrypting anything
([encrypted-headers.json](evidence/execution-20261028/encrypted-headers.json)).

The older [payload loader](evidence/execution-20261028/upgrade-encrypted-payload.dis.txt)
`U@0x64d4–0x6504` handles outer flag 4, rejects the signature/encrypted combination,
and requires a nonzero supplied context; the absent-context branch at
`U@0x6764–0x6784` returns error 48. It parses the header through `ZZ0053` at
`U@0x6718`, then initializes decryption through `ZZ0052` at `U@0x67a4`.
The captured [header parser](evidence/execution-20261028/crypto-encrypted-parser.dis.txt)
`C@0xa828–0xa8c0` checks that same magic/version and bounds the rest of the
structure; matching these fields establishes a format lead, not cross-version
implementation equivalence.

[Decryption setup](evidence/execution-20261028/crypto-encrypted-setup.dis.txt)
`C@0xae28–0xae88` obtains its key through the supplied callback then calls
`ZZ0075`. The supplied `ZZ0070` at `C@0xaee0–0xaee8` returns its first argument
unchanged; it does not derive a key from public signature anchors.
The [RSA decrypt wrapper](evidence/execution-20261028/crypto-rsa-decrypt.dis.txt)
`C@0x5bac–0x5c10` uses RSA private operation mode 1, and for scheme 1 configures
OAEP with hash selector 4 before `mbedtls_rsa_pkcs1_decrypt`. This is evidence of
a required caller-supplied RSA private-operation capability in this older path;
its provisioning/source and 57.23 applicability remain unproved. No private
key or decrypted key/payload was read, recovered or generated.

**Result:** the queued host-only experiment now establishes bounded header
structure and a concrete captured decryption gate. It does not produce a decoded
later rootfs, prove device access is necessary, or establish impossibility of
other offline extraction. Further progress needs a non-secret provisioning
trace or already-decoded matching capture; a magic-search miss is insufficient.
